# Physical layout: containers, internal columns and VSI

Sources: SPEC 3 and 7, `python/taco/container/`, `core/src/dataset.cpp`,
`core/src/cozip_index.cpp`, `core/src/sql.cpp`.

## Directory layout

Every FOLDER or ZIP dataset holds `DATA/`, `METADATA/` and `COLLECTION.json`. In a ZIP
these are entry prefixes; explicit directory entries are forbidden.

```
dataset/
├── DATA/
│   ├── 0/
│   │   ├── before/B02.tif
│   │   ├── after/B02.tif
│   │   └── mask.tif
│   └── 1/...
├── METADATA/
│   ├── sample.parquet
│   ├── children.parquet
│   ├── children__before.parquet
│   └── children__after.parquet
└── COLLECTION.json
```

Each sample is a directory named by its integer index, and every file is
`DATA/<idx>/<structure-path>`. Nothing else may live under `DATA/`: no placeholders,
no markers, no sidecars. Every dataset needs at least one sample, every sample at
least one declared file, and every stored file at least one byte, which is what
guarantees `DATA/` is represented by a stored path in both containers.

`METADATA/` holds one Parquet per level, the filename replacing every `/` with `__`.
Each Parquet schema stores its level name in the schema metadata key `taco:level`.
Parquet is written with zstd and statistics by default.

## Internal columns

`id` is unqualified because the specification defines it; the rest use `internal:`.
A producer supplies `Sample.id`, and the writer creates the physical `id` column and
all `internal:` columns. None of them may be declared as user metadata.

| Column | Type | Nullable | Present in |
| --- | --- | --- | --- |
| `id` | `string` | no | `sample.parquet` only |
| `internal:current_id` | `uint64` | no | every level |
| `internal:parent_id` | `uint64` | no | every level except `sample` |
| `internal:relative_path` | `string` | no | every level |
| `internal:offset` | `uint64` | yes | ZIP and TACOCAT child levels |
| `internal:size` | `uint64` | yes | ZIP and TACOCAT child levels |
| `internal:source_file` | `string` | no | TACOCAT only |

- `internal:current_id` **equals the row position** in its own Parquet file. Sample
  rows follow writer input order; child rows are grouped by parent and follow
  structure order.
- `internal:parent_id` points at `internal:current_id` in the parent level, so a join
  is `child."internal:parent_id" = parent."internal:current_id"`.
- `internal:relative_path` is relative to `DATA/`: `<idx>` for a sample row,
  `<idx>/<structure-path>` for a child. TACOCAT keeps the value the source archive
  had, so after reindexing a row still addresses its own archive.
- `internal:offset` and `internal:size` are null on folder rows and absent from
  `sample.parquet`, whose rows are sample roots rather than files. The offset is
  measured from byte 0 of the archive.

`taco:sample_index` is **generated by the reader**, never stored. For one container it
equals `internal:current_id` in `sample.parquet`; for a source list it is assigned
across sources in list order then row order. `cozip:location`, `taco:location` and
`taco:sample_index` are reserved reader names: a producer must not store them, and a
reader strips them from what it projects.

## VSI paths

TACO defines the path convention, not the library that resolves it. GDAL, rasterio,
QGIS, terra, sf, ArchGDAL and karu all read these.

| Prefix | Meaning |
| --- | --- |
| `/vsicurl/https://...` | HTTP object |
| `/vsis3/bucket/key`, `/vsigs/`, `/vsiaz/` | S3, Google Cloud, Azure |
| `/vsihf/datasets/org/repo/path` | Hugging Face |
| `/vsisource/account/product/key` | Source Cooperative |
| `/vsisubfile/<offset>_<size>,<path>` | A byte range of another path |

The reader composes them: a ZIP row becomes
`/vsisubfile/{offset}_{size},{archive}`, where the archive may itself be
`/vsicurl/https://...`. A FOLDER row needs no Parquet lookup for its path and becomes
`{root}/DATA/{idx}/{structure-path}`. A TACOCAT row combines the catalog's parent
directory with `internal:source_file`.

## ZIP container

A TACO archive is a valid ZIP that any tool can open, and satisfies the complete TACO
profile of CoZIP 1.1.0:

- the first entry is `__cozip__`, starting at byte 0, declaring **profile 2** and
  carrying offsets to `COLLECTION.json` and every `METADATA/*.parquet`;
- those priority files form the final contiguous entry block before the central
  directory, so a reader fetches them in one batch of ranges;
- **every entry uses STORE**, because `/vsisubfile/` reads stored bytes directly.
  Compression is invalid;
- the archive comment is empty and duplicate entries are forbidden.

Readers identify a TACO archive by the profile byte, not the `.zip` suffix, though the
Python writer requires that suffix for a predictable output mode.

STORE mode keeps the original file bytes inside a rebuilt archive, so a
content-defined-chunking platform such as Hugging Face Xet re-uploads only the chunks
that changed. Producers who rebuild often should prefer CDC-aware storage.

ZIP is immutable. Any change means rebuilding the archive.

## FOLDER container

A plain directory with the same logical layout, minus the byte offsets. It is the only
container that supports appending: new `DATA/<idx>/` directories are added, the
Parquet files are rewritten, and `COLLECTION.json` is updated, all published as one
completed update. A failed append leaves the previous dataset untouched.

Build FOLDER, publish ZIP.

## TACOCAT

```
.tacocat/
├── sample.parquet
├── children.parquet
├── children__before.parquet
└── COLLECTION.json
```

A catalog makes several ZIP partitions queryable as one collection. It has no `DATA/`
and no `METADATA/`; the Parquet files sit at its root. A reader accepts either the
`.tacocat/` directory or the parent directory containing it.

Consolidation reassigns `internal:current_id` from zero across the combined table and
rewrites `internal:parent_id` to match, so identifiers are global within each
consolidated file. `internal:source_file` names the origin archive, and
`internal:relative_path` and `id` are unchanged:

```
source_file | current_id | id          source_file | current_id | parent_id | relative_path
a.zip       | 0          | lima-01     a.zip       | 0          | 0         | 0/image.tif
a.zip       | 1          | lima-02     a.zip       | 1          | 1         | 1/image.tif
b.zip       | 2          | cusco-01    b.zip       | 2          | 2         | 0/image.tif
```

Row 2 still reads `0/image.tif` inside `b.zip`.

`taco:sources` records the partitions and must appear in TACOCAT and nowhere else:

```json
{"taco:sources": {"samples": 300000, "partitions": [
  {"file": "europe.zip", "samples": 100000,
   "spatial": [-10, 30, 45, 70],
   "temporal": ["2023-01-01T00:00:00Z", "2023-12-31T23:59:59Z"]}]}}
```

Each `file` is resolved against the directory **containing** `.tacocat/`, must be
unique, must match `internal:source_file`, and must be a normalized relative POSIX
path ending in `.zip`. `../europe.zip`, `/data/europe.zip` and `partitions\europe.zip`
are all invalid. `samples` must equal the sum of the partition counts. Every partition
must share the `id`, contract and collection metadata; only `extent` and
`taco:sources` may differ, and the consolidated extent is their union.

## Extent

`extent.spatial` is `[west, south, east, north]` in EPSG:4326, and `west > east` means
the dataset crosses the antimeridian. `extent.temporal` is null or
`[start, end]` as ISO 8601 UTC.

The writer produces `extent` from the shallowest level carrying a spatial profile, and
omits it when no level has one. It summarizes **sample centroids**, so it is an index
of sample centers, not the union of their footprints. Each ZIP partition summarizes
only its own rows; a FOLDER append summarizes old and new rows together.

## Why Parquet

One file per level, each independently queryable. Predicate pushdown skips row groups
that cannot match a filter, so `WHERE "quality:cloud_cover" < 10` reads a fraction of
the file; projection pushdown reads only the requested columns. Opening a dataset
never materializes all metadata.
