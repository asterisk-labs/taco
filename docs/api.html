API

Python writes TACO datasets and reads them. R and Julia read them through the same C core, and JavaScript reads them on its own. This page covers what they share. Each language page has the calls and examples.

How it works

A TACO dataset is a list of samples. A sample is one training or evaluation example: the files that belong together, such as two images and a change mask, and the metadata that describes them. One contract, declared before the first sample is written, fixes which files every sample holds and which fields each level stores. The writer refuses a sample that does not fit, so every reader can trust the shape of every sample.

The figures below use a dataset of two samples written with the Python writer. The figures on the landing page use Major TOM Core-DEM, a public dataset of 1,735,044 samples on Source Cooperative, read with the reader in Python on a laptop. Step through each figure with the names under it or the arrow keys.

A reader never lists DATA/. It reads COLLECTION.json and the Parquet files, filters them with SQL, and builds the location of every file it returns from the row, so nothing is extracted. For Major TOM Core-DEM, the first open downloads 70.3 MB of metadata for 1,735,044 samples, which took between 55 s and 101 s in three runs here, and about 2 s once cached. A query for the samples in Peru above 4,500 m then keeps 492 of them in 14 ms, and their files are 492 byte ranges, 16.5 MB of the 23.6 GB of DEM files.

The specification allows one writer, the Python package (spec 8). Readers may be written in any language, and every reader returns the same columns in the same order for the same dataset.

Only Python writes. It adds open_writer, validate, export and consolidate, described on the Python page and summed up below. Julia keeps its functions unexported, so they are called as Taco.read and Taco.sql.

Contract

The contract has two parts: the structure, which lists the files of a sample, and the metadata schema, which lists the fields of each level. It is stored in COLLECTION.json as taco:structure and taco:metadata, and it never changes. A change to the structure, a field, a type or the meaning of a field makes a different dataset that needs a new id (spec 6).

declarationmeans
mask.tifOne file, in every sample.
before/B02.tifOne file in the folder before/. Folders follow from the paths.
img*[4,16].tifA variable sequence: img0.tif to img{k-1}.tif with no gaps, where 4 ≤ k ≤ 16 and no index has a leading zero. The * is an index, not a glob.

Paths are relative POSIX paths of printable ASCII, so the same contract works in a folder and in a ZIP. A name cannot hold < > : " \ | ?, end with a space or a period, or contain __, and *, [ and ] appear only in a sequence. Two names in a folder that differ only in letter case conflict, because case-insensitive file systems and SQL treat them as one (spec 5.2 and 5.3).

The order of the structure matters. A folder takes the place of its first path, and child rows follow that order, so the levels in the figure list before, after, then mask.tif.

Metadata

Every level of the structure is a level of metadata: sample, children, and children/<folder> for each folder, stored as METADATA/sample.parquet, children.parquet and children__before.parquet. A level may have no fields of its own. Each field has a qualified name, an Arrow type, a nullability and a description.

ruleso
A field is namespace:field, with one :, the namespace matching [a-z][a-z0-9_]*.split:split, quality:cloud_cover. In SQL every such name goes in double quotes.
Types are canonical Arrow names: double, timestamp[us, UTC], list<int64>, struct<lon: float, lat: float>.A stored column must match exactly: an int32 column is invalid for an int64 field even when every value fits.
Nested values are not nullable unless they end in ?.list<int64?> allows null items; top-level nullability is the field's own flag.
The taco, internal and cozip namespaces are reserved, and so are id, taco:sample_index, taco:location and cozip:location.The writer adds id and the internal: columns; the reader computes the rest.
Names are unique in a level, ignoring case.SQL cannot tell quality:score from quality:Score.

The writer adds these columns to every level (spec 7.2):

columninholds
idsampleThe producer's identifier of the sample, unique in the dataset and kept by export and consolidation.
internal:current_idevery levelThe row's position in its Parquet file.
internal:parent_idevery level but sampleThe internal:current_id of the parent row.
internal:relative_pathevery levelThe path under DATA/: 1 for a sample, 1/before/B02.tif for a file.
internal:offset, internal:sizechild levels of a ZIP or TACOCATThe byte range of the file in its ZIP, null for folder rows.
internal:source_filea TACOCATThe ZIP partition that holds the row.

Collection metadata describes the whole dataset and lives in COLLECTION.json only: id, description, licenses and providers, which every dataset has, then tasks, title, curators, keywords and qualified fields such as source:mission. The writer adds extent and extension summaries such as split:counts from the rows it writes (spec 5.5).

Extensions

An extension gives a namespace a published meaning, and is identified by the URL of its JSON Schema, such as https://asterisk.coop/taco/spec/extensions/stac/v1.0.0/schema.json. The dataset lists the extensions it uses in taco:extensions. Some compute their columns while the writer runs, from the fields and files of each row, and some summarize their rows into collection fields. A reader needs none of them to read a dataset (spec 5.7).

extensionnamespacesstores
STACspatial, temporal, stacWhere and when a sample was taken: a grid or a footprint, a datetime or a range. The writer adds the centroid and the collection extent.
RumirumiThe external header of each Rumi file and, if asked, statistics, read back as {file}::header and {file}::mean.
MajorTOMmajortomThe Major TOM grid cell of each sample's centroid.
GeoEnrichgeoenrichValues at each sample's position from global layers: elevation, climate, soil, population, country.
Splitsplittrain, validation, test or excluded per sample, counted in split:counts.
InstrumentinstrumentThe bands of each file and the instruments that took them.
LabelslabelsThe class name of each value in a label file.
MLmlWhich files or fields are model inputs and which are targets.

A namespace that no listed extension owns is yours: its fields are valid and carry the meaning you give them in their descriptions.

Containers

The same dataset can be stored three ways, and every reader opens all three with the same call.

Build a dataset as a FOLDER and publish it as a ZIP (spec 6.1). The two hold the same samples, and only the ZIP metadata carries the byte offsets that make one file one range request. A ZIP is never modified: a change means writing it again. Because every entry is stored as it is, a platform that deduplicates by content, such as Hugging Face, uploads only the chunks that changed.

The writer partitions a ZIP by size, by a field such as split:split, or both, and consolidate joins ZIPs written separately. In a TACOCAT, internal:current_id and internal:parent_id are renumbered across partitions, while internal:relative_path and id keep their values, so each row still addresses its own ZIP (spec 7.5).

Read

read returns one row per sample, ordered by taco:sample_index. files limits which files get a location column; the metadata columns stay. A fixed file is named by its whole path, such as before/B02.tif, and a sequence by its declaration, such as img*[4,16].tif.

columnholds
source_fileThe ZIP of the sample, only for a TACOCAT or a list of sources.
taco:sample_indexThe sample's position, as uint64. The reader numbers the samples; it is not stored.
idThe producer's identifier.
sample fieldsIn the order of sample.parquet.
{file}::locationOne per file of the structure, in structure order, such as before/B02.tif::location. A sequence img*[4,16].tif is one list column, img::location, in index order.
{file}::header, {file}::meanAfter the location, the columns an extension generates for that file, such as the Rumi header and statistics.

Generated names carry ::, which no field can hold, since a field has exactly one :. Collection metadata is not repeated on each row: it is the dataset's collection.

id is the identity of a sample. taco:sample_index is only a position: it starts at zero in every dataset, and for a list of sources it runs across them in list order, so reversing the list renumbers every sample. Store and cite id, never the index.

A list of sources opens compatible ZIPs as one dataset. Each must have the same collection, ignoring extent, and a path may appear once. A list does not check that id is unique across parts; consolidate does. A TACOCAT is opened by its own path, never inside a list.

SQL

sql runs one DuckDB query over the relation dataset, which is exactly what read returns, and one relation per level, named like the level. The level relations are raw: they keep the internal: columns and have no locations.

SELECT id, "dem.rumi::location"
FROM dataset
WHERE "geoenrich:admin_countries" = 'Peru' AND "geoenrich:elevation" > 4500
ORDER BY "geoenrich:elevation" DESC
  • Quote every field and every level with a /: "split:split", FROM "children/before". Without quotes DuckDB fails to parse the query.
  • Join a level to its parent with child."internal:parent_id" = parent."internal:current_id", and use aliases when a field name appears at two levels.
  • Add ORDER BY when order matters. Only read promises an order.
  • An error in the query is a DuckDB error, such as a parser or catalog error, not a TACO error.

The query above, run on Major TOM Core-DEM with Python on a laptop, takes 14 ms and returns 492 rows. The highest is MT10km_0137D_0827L, at 5,635 m.

Sources and cache

Python, R, Julia and C read through Karu, so a source is a local path or one of these URLs. A location keeps the form of its source:

sourcea location built from it
data/tiny.zip/vsisubfile/412_66,/home/me/data/tiny.zip, since Python makes a local path absolute
https://host/tiny.zip/vsisubfile/412_66,/vsicurl/https://host/tiny.zip
s3://bucket/tiny.zip, gs://, az:///vsisubfile/412_66,/vsis3/bucket/tiny.zip, and /vsigs/, /vsiaz/
hf://datasets/org/repo/tiny.zip/vsisubfile/412_66,/vsihf/datasets/org/repo/tiny.zip
source://account/product/tiny.zip/vsisubfile/412_66,/vsisource/account/product/tiny.zip
a FOLDER, such as tiny//home/me/tiny/DATA/0/before/B02.tif

Opening a remote dataset copies its metadata, never its files. For a ZIP the reader reads the index at byte 0, then fetches COLLECTION.json and every Parquet range in one batch. For a remote FOLDER or TACOCAT it fetches the files that taco:metadata names, since it never lists a directory. A local ZIP has its metadata extracted to a temporary directory for the process, and a local FOLDER or TACOCAT is read in place.

variabledoes
TACO_CACHE_DIRWhere remote metadata is kept. By default $XDG_CACHE_HOME/taco, else ~/.cache/taco.
TACO_CACHE_SIZEThe most bytes the cache keeps, 5 GiB by default. The entries opened least recently go first.
TACO_CACHE_REFRESHAny value rebuilds the entries a call opens.

Before it uses a cached entry, the reader checks the size the server reports for the source, and builds the entry again when it changed. If that check fails, the open fails. An open dataset is a snapshot of the metadata it loaded. Credentials come from where the usual tools keep them, as Karu's configuration page lists: HF_TOKEN or the Hugging Face login, the AWS variables and profiles, Google application default credentials and the Azure storage variables. The JavaScript reader uses fetch, so it reads public and presigned URLs.

Open a file

A location is a VSI path, the convention GDAL uses (spec 3.2). /vsisubfile/offset_size,archive names size bytes from offset in the archive, so a reader that understands it fetches only that file. GDAL, rasterio, terra and sf open the /vsicurl/, /vsis3/, /vsigs/ and /vsiaz/ forms. /vsihf/ and /vsisource/ are Karu's names, which Rumi reads; for GDAL, open the dataset through its https:// URL instead.

Major TOM Core-DEM stores Rumi files. Rumi reads a location, with the header the dataset keeps beside it:

import rumi, taco

ds = taco.open_dataset("https://data.source.coop/major-tom/core-dem/")
row = ds.sql("SELECT * FROM dataset WHERE id = 'MT10km_0100D_0854L'").to_pylist()[0]
dem = rumi.read(row["dem.rumi::location"], row["dem.rumi::header"])
dem.shape, dem.min(), dem.max()
((1, 352, 352), np.int16(3784), np.int16(5840))

Any client that reads a byte range reads the file too. HTTP ranges include their last byte, so the range is offset to offset + size - 1: the location above, /vsisubfile/577605662_48266,..., is Range: bytes=577605662-577653927.

Validate, export, consolidate

The Python package has three more calls that work on whole datasets.

calldoes
taco.validate(path)Checks a local FOLDER, ZIP or TACOCAT against every rule of spec 7.6, the payloads included, and reports every problem it finds rather than the first.
taco.export(source, out, sql=...)Writes the samples a query selects as a new dataset. A row selects its whole sample, which keeps its id and gets a new index, and the writer computes the extent again.
taco.consolidate(sources, out)Joins ZIPs written separately into a TACOCAT, after checking that they share the id, the contract and the collection metadata and that no sample id repeats.

A reader also refuses what it meets that breaks the specification, but it does not read every file before it answers a query, so validate is the check to run before publishing.

Errors

Python raises a subclass of taco.TacoError for problems with a container, a contract or a sample, and DuckDB's own errors for a bad query. R raises plain errors and Julia ArgumentError or ErrorException, with the same messages, and JavaScript a TacoError with a code. Each language page lists them.

errorcause
ContainerErrorA source that cannot be opened or is not a valid dataset, an unknown files entry, a TACOCAT inside a list.
ContractErrorA structure or schema that breaks the rules, such as a bad name, a reserved namespace or a type that is not canonical.
CollectionErrorCollection metadata that is missing or invalid.
SampleErrorA sample that does not fit its contract: a missing or undeclared file, an empty file, a value of the wrong type.
WriterErrorA writer used outside its lifecycle, such as add after run, or a publish that failed.
ConsolidationErrorPartitions that cannot be joined.
ValidationFailedA validation report with errors, from raise_for_errors.

Hosting

Upload the ZIP, or the partitions and the .tacocat/ folder beside them, to a bucket, Hugging Face or Source Cooperative. Publish a new version at a new path or revision, because readers keep cached metadata and offsets of the old one, and pin revisions in training runs.

requirementwhy
Answer Range with 206 and the stored bytes.Readers fetch the index, the metadata and each file as ranges.
Apply no Content-Encoding.Offsets and sizes refer to the stored bytes.
Report the object's size.The reader compares it with its cached entry.
For browsers, allow Range across origins and expose Content-Range.The JavaScript reader and the playground need both.

A TACO ZIP is a cozip, so cozip.verify checks its index and hash from the URL. It took 1.6 s for a 1.23 GB partition of Major TOM Core-DEM. Then paste the URL into the playground to browse it.
