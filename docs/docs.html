The example

This page follows one small dataset from start to end. It holds three samples of a change detection task over Lima. Each sample has an image taken before the change, an image taken after it, and a mask of what changed. The code writes the files from bytes, so it runs anywhere pip install "taco-eo[writer]" does.

from datetime import datetime, timezone
from typing import Annotated

import pyarrow as pa
from pydantic import BaseModel, Field

import taco
from taco.extensions.sample.split import Split

TimestampUTC = Annotated[datetime, pa.timestamp("us", tz="UTC")]
UTC = timezone.utc


class Scene(BaseModel):
    date: TimestampUTC = Field(description="Acquisition time")


class Band(BaseModel):
    name: str = Field(description="Band name")


contract = taco.Contract(
    structure=["before/B02.tif", "after/B02.tif", "mask.tif"],
    metadata=[
        taco.Level("sample", split=Split),
        taco.Level("children", scene=Scene | None),
        taco.Level("children/before", band=Band),
        taco.Level("children/after", band=Band),
    ],
)
collection = taco.Collection(
    contract=contract,
    id="lima-change",
    description="Before and after images of Lima with a change mask",
    licenses=["CC-BY-4.0"],
    providers=["Example Lab"],
    tasks=["change-detection"],
)

rows = [
    ("lima-0001", "train", datetime(2024, 1, 5, tzinfo=UTC), datetime(2024, 7, 5, tzinfo=UTC)),
    ("lima-0002", "validation", datetime(2024, 2, 10, tzinfo=UTC), datetime(2024, 8, 10, tzinfo=UTC)),
    ("lima-0003", "test", datetime(2024, 3, 15, tzinfo=UTC), datetime(2024, 9, 15, tzinfo=UTC)),
]
with taco.open_writer(collection, "lima.zip", overwrite=True) as writer:
    for sample_id, split, before, after in rows:
        writer.add(
            taco.Sample(
                id=sample_id,
                metadata=taco.Metadata(split=Split(split=split)),
                folders=[
                    taco.Folder("before", metadata=taco.Metadata(scene=Scene(date=before))),
                    taco.Folder("after", metadata=taco.Metadata(scene=Scene(date=after))),
                ],
                assets=[
                    taco.Asset(f"{sample_id} before".encode(), path="before/B02.tif", metadata=taco.Metadata(band=Band(name="B02"))),
                    taco.Asset(f"{sample_id} after".encode(), path="after/B02.tif", metadata=taco.Metadata(band=Band(name="B02"))),
                    taco.Asset(f"{sample_id} mask".encode(), path="mask.tif"),
                ],
            )
        )
    result = writer.run()

result.samples, result.data_files, result.metadata_files, result.size
(3, 9, 4, 32819)

What TACO is

A training example in Earth observation is rarely one image. A CloudSEN12 sample combines Sentinel-2 Level-1C and Level-2A images with Sentinel-1 data and a cloud mask drawn by hand. A change detection example pairs the bands taken before an event with the bands taken after it and a map of what changed. A time series holds as many scenes as the sensor took over the period.

Each dataset arranges these files in a tree of its own, and its metadata follows that tree. Some fields belong to the whole sample, such as its position or its split. Others belong to one folder or one file, such as the date of a scene or the name of a band.

Libraries such as TorchGeo, TerraTorch and torchange wrap each dataset in a loader class of its own. Every loader repeats the convention its dataset invented: which row of a CSV describes which file, and where that file sits.

TACO, Transparent Access to Cloud-Optimized datasets, writes that convention into the dataset. From Earth observation it takes metadata that can be filtered by place and time, and direct access to files on disk or over HTTP. From machine learning it takes the training example as the unit. A dataset is a list of samples that share one declared tree, and one reader opens all of them.

Three existing formats carry it:

ParquetThe metadata, one table per level of the tree. DuckDB queries it in process, with no server.
cozipThe ZIP that holds a dataset, with an index at byte 0, so a reader finds the metadata in one batch of range requests.
GDAL VSI pathsThe location of every file: a path that names a byte range inside the archive, local or remote.

The contract

Before the first sample is written, the producer declares a contract. It has two parts. The structure lists the files of every sample and, through their paths, the folders that hold them. The metadata schema lists the typed fields of each level. In the example:

taco.Contract(
    structure=["before/B02.tif", "after/B02.tif", "mask.tif"],
    metadata=[
        taco.Level("sample", split=Split),
        taco.Level("children", scene=Scene | None),
        taco.Level("children/before", band=Band),
        taco.Level("children/after", band=Band),
    ],
)

Folders follow from the paths, so this structure has two, before/ and after/. A path can also declare a bounded sequence: img*[4,16].tif means img0.tif to img{k-1}.tif with no gaps, where k is between 4 and 16. That is how a time series whose length changes from sample to sample keeps one contract (spec 5.2).

The writer checks every sample against the contract and refuses one that does not fit. A fourth sample without its mask stops at add:

SampleError: required asset 'mask.tif' is missing

A sample fits when each fixed file appears once, each sequence has a count within its bounds, no file falls outside the structure, files keep the order of the structure, and every row has the fields of its level with their types. Each rule looks at one sample alone, never at its neighbours, and the guarantees below rest on that.

The contract is stored in COLLECTION.json and never changes. Adding a file, a field or a type makes a different dataset, with a new id (spec 6). The API page has the naming rules.

One table per level

The sample and each folder of the structure is a level. The metadata of a level is one Parquet table, with one row for each of its children in every sample. Step through the figure with the names under it, a click, or the arrow keys.

The contract fixes these tables before any sample is written: one for the samples and one for each folder of the structure, four here. A reader knows every column of every table from COLLECTION.json alone. Field names carry a namespace, such as split:split or scene:date, and the API page lists the columns the writer adds.

The dataset relation that read returns joins these tables back into one row per sample. The raw tables stay open to SQL, so a query can filter on a level below the sample, here the date of the image after the change:

lima.sql("""
    SELECT s.id, c."scene:date"
    FROM sample s JOIN children c ON c."internal:parent_id" = s."internal:current_id"
    WHERE c."internal:relative_path" LIKE '%/after' AND c."scene:date" >= '2024-08-01'
    ORDER BY s.id
""").to_pylist()
[{'id': 'lima-0002',
  'scene:date': datetime.datetime(2024, 8, 10, 0, 0, tzinfo=zoneinfo.ZoneInfo(key='UTC'))},
 {'id': 'lima-0003',
  'scene:date': datetime.datetime(2024, 9, 15, 0, 0, tzinfo=zoneinfo.ZoneInfo(key='UTC'))}]

On disk

The file of sample i at structure path p lives at DATA/i/p. The place of a file follows from the index of its sample and its path, with no lookup and no directory listing. Two files never claim the same place, because names in a folder are unique and the index comes first.

lima/
├── COLLECTION.json                  the collection and its contract
├── METADATA/
│   ├── sample.parquet               3 rows
│   ├── children.parquet             9 rows
│   ├── children__before.parquet     3 rows
│   └── children__after.parquet      3 rows
└── DATA/
    ├── 0/
    │   ├── before/B02.tif
    │   ├── after/B02.tif
    │   └── mask.tif
    ├── 1/
    └── 2/

That directory is a FOLDER, the container to build in and the only one that accepts appends. A ZIP holds the same paths in one archive, every file stored uncompressed, and its tables add the offset and size of each file. A TACOCAT splits a dataset too large for one object into ZIP partitions, with one catalog beside them. Every reader opens all three with the same call, and the API page draws them byte by byte.

From a row to bytes

In a ZIP, the reader turns the offset and size of a row into a location, and the location into one byte range. Follow the after/B02.tif of lima-0002:

Anything that reads a byte range reads the file. GDAL, rasterio, terra and Rumi open the location as it is, and plain Python can seek:

with open("lima.zip", "rb") as f:
    f.seek(647)
    f.read(15)
b'lima-0002 after'

Over HTTP the same location is one range request, and the archive is never downloaded or extracted. How TACO reads follows a remote read request by request.

What the contract guarantees

Because each sample fits the contract on its own, the contract gives four properties, and the calls rely on them.

One table per levelThe contract alone fixes the tables and their columns: one for the samples and one per folder. A reader knows the schema before it reads a row.
One place per fileA file lives at DATA/i/p and no two files share a place. The files of a sample follow from the structure and the length of its sequences, with nothing read.
A subset is a datasetNo rule of the contract mentions another sample, so any selection of samples, numbered again from zero, still fits it. taco.export writes one.
Parts joinDatasets with the same contract and collection join into one, numbered in order. A list of sources opens them together, and taco.consolidate writes them as a TACOCAT.

The validation pair of the example, exported, keeps its contract and its id, and becomes sample 0:

taco.export(
    "lima.zip",
    "lima-validation.zip",
    sql="""SELECT * FROM dataset WHERE "split:split" = 'validation'""",
    id="lima-change-validation",
    description="The validation pairs of lima-change",
)
taco.read("lima-validation.zip").select(["taco:sample_index", "id", "split:split"]).to_pylist()
taco.open_dataset("lima-validation.zip").contract == lima.contract
[{'taco:sample_index': 0, 'id': 'lima-0002', 'split:split': 'validation'}]

Next to STAC

STAC is how Earth observation describes its data for discovery: Items whose assets link to files, usually one JSON document per Item. STAC-GeoParquet stores the same Items as rows of GeoParquet, so a large catalog can be filtered by column. TACO keeps the spatial and temporal fields of STAC through its STAC extension, and adds what a training example needs:

Machine learning formats come from the other side. Croissant describes the records of a dataset, and WebDataset streams examples from tar shards in order. Both treat the example as the unit, and neither filters by place and time before it reads.

Trade-offs

The contract is fixed when the dataset is created. A new file or field means a new dataset with a new id. Sequences let the number of files vary within bounds, but a sample cannot grow a structure of its own. Samples whose trees do not match go in separate datasets, or into one tree chosen before packaging.

A ZIP is never modified: a change means writing it again, and publishing it at a new path. In exchange every path is predictable, every row is checked against a schema, and a release reads the same way everywhere.
