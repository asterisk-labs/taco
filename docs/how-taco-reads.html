The example

The dataset has the contract of the overview, an image before, an image after and a change mask per sample, with 10,000 samples of 64 by 64 pixel GeoTIFFs. Its ZIP is 219,225,967 bytes. A small HTTP server that answers range requests serves it and logs every request it receives. Its local address is shown as https://host. The code opens the dataset, picks two validation samples with SQL and reads the first image after the change with rasterio:

import rasterio
import taco

ds = taco.open_dataset("https://host/lima10k.zip")
rows = ds.sql("""
    SELECT id, "after/B02.tif::location"
    FROM dataset
    WHERE "split:split" = 'validation'
    ORDER BY id
    LIMIT 2
""").to_pylist()
rows[0]
with rasterio.open(rows[0]["after/B02.tif::location"]) as src:
    src.crs.to_epsg(), src.read(1).shape
{'id': 'lima-00026', 'after/B02.tif::location': '/vsisubfile/577841_8552,/vsicurl/https://host/lima10k.zip'}
(32718, (64, 64))

The open moved 150,174 bytes, less than 0.07% of the archive, and nothing in the archive was downloaded or extracted. The sections below take the four steps in order.

1. Open

The reader never lists the archive and never parses its Central Directory, the table of contents a ZIP keeps at its end. A TACO ZIP is a cozip: the first entry, at byte 0, is an index of the entries a reader needs, here COLLECTION.json and the four Parquet tables. Step through the figure:

The cache lives in TACO_CACHE_DIR, by default ~/.cache/taco, one folder per dataset:

lima-change-10k-zip-http-.../
├── COLLECTION.json
├── METADATA/
│   ├── sample.parquet
│   ├── children.parquet
│   ├── children__before.parquet
│   └── children__after.parquet
└── taco-cache.json

A remote FOLDER has no index, so the reader asks for COLLECTION.json first and then for the Parquet files it names. A TACOCAT is read the same way from its .tacocat/ folder, which holds the metadata of every partition. Neither is ever listed (Sources and cache).

2. Query

A query runs in DuckDB, inside the process, over the cached Parquet tables. The query of the example sent no request. A filter by split, date, place or any other field costs nothing on the network, however many samples the dataset holds, and so does read.

The answer is a table with one row per sample. A file column holds a location, which is text: the reader has not touched a file yet.

3. Locate

The location of after/B02.tif in sample lima-00026 comes from its row in children/after, as the overview shows, and from the form of the source:

/vsisubfile/577841_8552,/vsicurl/https://host/lima10k.zip
            ^^^^^^ ^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
            offset size the archive, as GDAL names a URL

A source on S3, Google Cloud, Azure or Hugging Face gives /vsis3/, /vsigs/, /vsiaz/ or /vsihf/ in place of /vsicurl/ (API). Building it sends no request.

4. Fetch

The bytes are fetched by whatever opens the location. rasterio passed it to GDAL, which asked for the size of the URL once, with HEAD, then read the 16 KiB block that holds the file. GDAL reads /vsicurl/ in blocks of 16 KiB and keeps them, so the second file cost one request.

A plain HTTP client fetches exactly the file. A range includes its last byte, so it is offset to offset + size - 1:

import urllib.request

request = urllib.request.Request("https://host/lima10k.zip", headers={"Range": "bytes=577841-586392"})
data = urllib.request.urlopen(request).read()
len(data), data[:4]
(8552, b'II*\x00')

The four bytes are the start of a little-endian TIFF. The server logged one request, for 8,552 bytes.

Open again

The second open_dataset sent one request. It asked for the size of the archive, found the same 219,225,967 bytes stamped on the cache entry, and used the cached files. A size that changed rebuilds the entry, and so does TACO_CACHE_REFRESH. A dataset is never modified in place, so a new version belongs at a new URL, as Hosting says.

In a DataLoader

Open the dataset once, in the main process, and give the workers the locations. They are strings, so they cross into worker processes as they are, and each worker opens only the files of its samples:

import numpy as np
import rasterio
import taco
import torch
from torch.utils.data import DataLoader, Dataset

FILES = ["before/B02.tif", "after/B02.tif", "mask.tif"]


class LimaChange(Dataset):
    def __init__(self, source, split):
        columns = ", ".join(f'"{name}::location"' for name in FILES)
        self.rows = taco.open_dataset(source).sql(
            f"""SELECT {columns} FROM dataset WHERE "split:split" = '{split}' ORDER BY "taco:sample_index" """
        ).to_pylist()

    def __len__(self):
        return len(self.rows)

    def __getitem__(self, i):
        arrays = []
        for name in FILES:
            with rasterio.open(self.rows[i][f"{name}::location"]) as src:
                arrays.append(src.read(1).astype(np.float32))
        return torch.from_numpy(np.stack(arrays[:2])), torch.from_numpy(arrays[2])


if __name__ == "__main__":
    data = LimaChange("https://host/lima10k.zip", "validation")
    for images, masks in DataLoader(data, batch_size=32, num_workers=4):
        pass
    print(len(data), tuple(images.shape), tuple(masks.shape))
1021 (29, 2, 64, 64) (29, 64, 64)

One pass over the 1,021 validation samples read 3,063 files, 22.0 MB. The server logged:

requestsfrom
1The open in the main process, a size check, since the metadata was cached.
4 HEADGDAL, once in each worker.
2,177 ranges, 43.4 MBGDAL's 16 KiB blocks. The three files of a sample sit next to each other, so a block often holds two of them.

No request touched the metadata again, and no worker read a file outside its batch. GDAL trades bytes for requests here; its configuration options such as CPL_VSIL_CURL_CHUNK_SIZE tune the block size.

Where it lives

core/src/dataset.cppOpens a source, finds or builds its cache entry, and keeps the levels.
core/src/cozip_index.cppReads the index at byte 0 and checks its hash against the last 32 KiB.
core/src/transport.cppAsks Karu for sizes and batches of ranges, over HTTP, S3, Google Cloud, Azure or Hugging Face.
DuckDBRuns read and sql over the cached tables, with the SQL the core generates.
python/taco/reader/The Python reader over the C core. R and Julia load the same core, and JavaScript repeats these steps with fetch.
