Specification

The TACO Specification

Version 3.0.0 · Status Draft

1. Version

This document defines version 3.0.0 of the TACO specification. The specification follows Semantic Versioning. Implementations are versioned separately and declare which version of the specification they support.

TACO v3 is not compatible with v2 datasets. Annex A explains the differences and how to migrate.

1.1. Terminology

The words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" have the meanings defined by RFC 2119 when written in uppercase. All other text is explanatory.

2. Overview

TACO stands for Transparent Access to Cloud-Optimized datasets. It defines how Earth observation data and metadata are organized, stored, and accessed as one unit.

A machine learning dataset is more than a collection of files. It contains samples, and each sample may contain several files arranged in folders. Metadata may describe the sample, a folder, or an individual file. Existing formats cover parts of this model, but not the complete dataset.

STAC provides a logical model for geospatial data based on Catalogs, Collections, Items, and Assets. It represents that model as JSON, which works well for discovery and interoperability. At training-dataset scale, however, representing every sample as an Item may produce millions of JSON documents. Efficient access then depends heavily on caching.

STAC-GeoParquet stores STAC Items as rows in GeoParquet and their Assets as structs. This enables fast columnar queries without a server, but the result is still a flat table. For example, a change detection sample may contain a before/ folder, an after/ folder, and a change_map.tif label. STAC-GeoParquet cannot represent those folders as separate entities with their own metadata. It also stores metadata separately from the data files.

TACO models a dataset as a collection of samples that share one structure and metadata schema. Each sample has an integer index, and each file has a predictable path. Metadata is stored in a small set of Parquet files that can be queried with DuckDB.

3. Foundations

TACO combines three existing technologies. Apache Parquet stores queryable metadata. VSI paths identify data on local or remote storage. Cloud-Optimized ZIP packages data and metadata while preserving direct access to individual files.

A dataset may use one of three containers. FOLDER stores the dataset as a directory. ZIP stores a dataset or partition in one archive. TACOCAT combines the metadata of several ZIP partitions.

3.1. Apache Parquet

Apache Parquet stores values by column rather than by row. This lets a query avoid data it does not need.

Predicate pushdown uses row-group statistics to skip groups that cannot match a filter. A query such as WHERE "quality:cloud_cover" < 10 can therefore avoid reading most of the file.

Projection pushdown reads only the requested columns. Selecting two columns from a table of fifty does not require reading the other forty-eight.

TACO MUST store metadata in Parquet, with one file for each level of the sample hierarchy. Each file can be queried independently.

A reader MUST use predicate and projection pushdown when its query engine supports them. Opening a dataset does not require loading every Parquet file or materializing all metadata.

3.2. VSI Path Convention

TACO uses VSI paths to locate data. A VSI path describes how to reach a file on local disk, over HTTP, in object storage, or within a byte range of another file.

/vsicurl/https://example.com/scene.tif     reads from HTTP
/vsis3/bucket/scene.tif                     reads from S3
/vsigs/bucket/scene.tif                     reads from Google Cloud
/vsiaz/container/scene.tif                  reads from Azure

TACO mainly uses /vsisubfile/, which identifies a byte range by its offset and size.

/vsisubfile/1024_4096,/data/archive.zip

This path reads 4096 bytes at offset 1024 from archive.zip. It does not extract the archive. VSI paths can also be combined to read a byte range from a remote file.

/vsisubfile/1024_4096,/vsicurl/https://hf.co/dataset.zip

A reader MUST construct VSI paths when data is accessed. For ZIP containers, it reads the offset and size from Parquet metadata. For FOLDER containers, it builds the path directly from the contract and sample index, such as DATA/42/before/B02.tif.

TACO defines the path convention, not the library that resolves it. GDAL supports VSI paths through tools and libraries such as rasterio, QGIS, gdalwarp, sf, terra, and ArchGDAL. Other implementations are valid if they interpret the same paths and perform the required reads.

3.3. Cloud-Optimized ZIP

A cloud-optimized ZIP is a valid ZIP archive that any standard ZIP tool can open. It adds an index at byte 0 with direct offsets to the metadata files. A TACO reader can use this index without first reading the ZIP Central Directory at the end of the archive.

The index points to the Parquet metadata. The metadata then provides the offsets and sizes needed to access individual data files.

A TACO ZIP MUST index every Parquet file in METADATA/ and COLLECTION.json. Every entry MUST use STORE mode without compression. The /vsisubfile/ convention reads raw byte ranges, so compressed entries cannot provide direct access and are invalid.

STORE mode also works well with Content-Defined Chunking on platforms such as Hugging Face. Because unchanged files keep the same raw content inside a rebuilt archive, the platform can often upload only the chunks that changed. Producers SHOULD use a CDC-aware platform when publishing frequently updated ZIP datasets.

4. Design Goals

TACO is guided by five design principles.

Self-contained and portable. Data and metadata live together in a ZIP file or directory. Using the dataset does not require a database, API server, or external catalog.

Cloud-optimized. Readers can filter metadata and access individual files with partial reads. They do not need to download or extract the complete archive.

Contract-first. The contract declares the files and metadata expected in every sample. Writers use it to reject missing files, unexpected fields, and inconsistent layouts.

FAIR-compliant. TACO supports the FAIR principles through descriptive metadata, identifiers, licensing, spatial and temporal extents, Parquet, and VSI paths.

Language-agnostic. The reader is a DuckDB extension. Any language with a DuckDB client can use the same SQL interface.

4.1. Tradeoffs

TACO assumes that every sample in a dataset follows the same contract. The contract is fixed for a dataset version, although new samples may be added as long as they preserve its structure and metadata schema.

This constraint makes the dataset predictable. Readers know which files and metadata levels exist, and the writer can reject incomplete or inconsistent samples.

Changing the structure, adding metadata fields, or changing field types requires a new dataset version. TACO is not a good fit when samples need to evolve independently within the same version.

5. Data Model

The data model has two parts. The structure defines the files in each sample. The metadata schema defines the fields stored at each level.

5.1. Contract

The contract combines the structure and metadata schema of a dataset. It MUST be declared before any sample is written, and every sample MUST follow it. The contract cannot change within a dataset version.

5.2. Structure

The structure defines which files belong to a sample and how they are arranged in folders. It is stored in taco:structure as a list of relative file paths. Folders are inferred from the path segments.

Each path describes either a fixed file or a variable sequence of files.

A fixed file appears exactly once in every sample. Its name is written directly in the structure, such as B02.tif.

A variable sequence allows the number of files to differ between samples. It uses the form prefix*[a,b].ext, where a is the minimum number of files and b is the maximum. The prefix is required and 0 <= a <= b.

The * represents a zero-based index, not a filesystem glob. If a sample contains k files, their names MUST run from prefix0.ext to prefix{k-1}.ext without gaps, where a <= k <= b.

Entries in the same folder MUST have unique identifiers. A fixed file uses its full name as the identifier. A variable sequence uses its prefix.

Examples

Single file. When taco:structure is null, each sample is one file with no internal structure.

{ "taco:structure": null }

Fixed files. Each CloudSEN12 sample contains the same three files.

{
  "taco:structure": [
    "s2_l1c.tif",
    "s2_l2a.tif",
    "target.tif"
  ]
}

Folders. Each change detection sample contains two folders and one label.

{
  "taco:structure": [
    "before/B02.tif",
    "before/B03.tif",
    "before/B04.tif",
    "after/B02.tif",
    "after/B03.tif",
    "after/B04.tif",
    "change_map.tif"
  ]
}

Variable sequence. Each multitemporal sample contains between 4 and 16 images.

{ "taco:structure": ["img*[4,16].tif"] }

Each sample contains 4 to 16 files named img0.tif, img1.tif, and so on, with no gaps in the sequence.

Fixed and variable files. The same folder may contain both forms.

{
  "taco:structure": [
    "before/B02.tif",
    "before/B03.tif",
    "before/B04.tif",
    "before/mask*[1,5].tif"
  ]
}

The identifiers inside before/ are B02.tif, B03.tif, B04.tif, and mask. Each is unique.

5.3. Reserved Characters

TACO reserves three tokens so that paths, levels, and metadata fields can be mapped without ambiguity.

TokenPurposeRule
:Separates a namespace from a field nameEvery user field MUST contain exactly one. It MUST NOT appear in folder names, file names, or level keys.
/Separates path and level segmentsIt MAY appear in complete structure paths and level keys. It MUST NOT appear inside a folder or file name.
__Replaces / in Parquet filenamesIt MUST NOT appear in folder names, file names, namespaces, or metadata field names.

For example, the level children/before is stored in children__before.parquet.

5.4. Metadata

The metadata schema defines the columns stored at each level. It is written to taco:metadata, where each level maps field names to their declarations.

Every field MUST declare the following properties. Its type MUST be representable in Apache Parquet.

PropertyTypeMeaning
typestringCanonical Arrow type
nullablebooleanWhether the stored column may contain null values
descriptionstringHuman-readable field description; MAY be empty

A level identifies what each row describes.

LevelRows
sampleOne row per sample
childrenOne row per direct child of a sample
children/<folder>One row per direct child of that folder in every sample

Names after children/ come from the folders in taco:structure. For example, children/before contains one row for every file directly inside each before/ folder. A single-file contract has only the sample level.

taco:metadata MUST include sample and every child level implied by the structure. A level with no user fields is stored as an empty object.

Each level becomes one Parquet table. Rows from all samples are stored together and linked to their parents with internal:parent_id.

Every user column MUST follow the type and nullability declared in the contract. A non-empty description MUST be stored in the Arrow field metadata under description.

Namespaces

Every user field MUST use the form namespace:field. A namespace groups related fields but does not assign behavior. Both parts MUST be non-empty, and the qualified name MUST be unique within its level.

The same namespace MAY appear at multiple levels and MAY use a different schema at each level. The internal and taco namespaces are reserved. Producers MUST NOT create fields in either namespace.

The namespace remains part of the Parquet column name. It does not create a nested struct or refer to a Python class. Contracts are equivalent when their levels, qualified field names, types, nullability, and descriptions are the same.

5.6. Properties

Deterministic paths. A sample index and a structure path identify every file. In FOLDER mode, they produce a path such as DATA/42/before/B02.tif. In ZIP mode, Parquet metadata provides the offset and size for a VSI path. The cost of locating that metadata depends on the Parquet reader and file layout.

Safe partitioning. Any subset of samples remains valid under the same contract.

Simple concatenation. Collections with identical contracts can be combined by appending and re-indexing their samples.

6. Dataset Versioning

The dataset_version in COLLECTION.json MUST follow Semantic Versioning. Compatibility is measured from the reader's perspective. A change is backward compatible when code written for the previous version continues to work without modification.

6.1. Version Levels

PATCH such as 1.0.0 to 1.0.1 corrects existing content without changing the contract or adding samples. Examples include fixing metadata values, replacing corrupted files, or updating the description, keywords, or extent.

MINOR such as 1.0.0 to 1.1.0 adds samples under the existing contract.

MAJOR such as 1.0.0 to 2.0.0 extends the contract without removing existing structure. Examples include adding files, folders, or metadata fields. Existing readers can ignore the additions, but readers that validate the complete contract may need to update their expectations.

6.2. When to Create a New Dataset

A breaking contract change requires a new dataset with a new id. This includes removing or renaming files or metadata fields, changing field types, and reorganizing the sample hierarchy.

The rule is simple. If existing reader code still works, increment the version. If it does not, create a new dataset.

6.3. Container Mode and Mutability

FOLDER containers support appending samples. New data is added under DATA/, new rows are added to METADATA/, and COLLECTION.json is updated. This mode is suitable for datasets under active development or continuous ingestion.

ZIP containers are immutable and must be rebuilt after any change. They are suitable for stable releases. On CDC-aware platforms, rebuilding a ZIP may transfer only the chunks that changed.

Producers SHOULD build datasets as FOLDER containers and publish stable versions as ZIP containers. Conversion changes only the packaging.

7. Physical Layer

This section defines how a TACO dataset is stored.

7.1. Directory Structure

Every TACO dataset MUST contain DATA/, METADATA/, and COLLECTION.json.

dataset/
├── DATA/
│   ├── 0/
│   │   ├── before/
│   │   │   ├── B02.tif
│   │   │   ├── B03.tif
│   │   │   └── B04.tif
│   │   ├── after/
│   │   │   ├── B02.tif
│   │   │   ├── B03.tif
│   │   │   └── B04.tif
│   │   └── change_map.tif
│   ├── 1/
│   │   └── ...
│   └── ...
├── METADATA/
│   ├── sample.parquet
│   ├── children.parquet
│   ├── children__before.parquet
│   └── children__after.parquet
└── COLLECTION.json

DATA/ contains the data files. Each sample MUST use a directory named by its integer index. Its contents MUST follow taco:structure.

METADATA/ contains one Parquet file for each key in taco:metadata. The filename replaces every / in the level name with __.

COLLECTION.json contains the dataset description and contract defined in Section 5.5.

7.2. Internal Columns

TACO adds columns for row relationships and data access. Their names use the reserved internal: namespace, which users MUST NOT use.

ColumnDescriptionPresent in
internal:current_idRow index within this Parquet (0-indexed)All Parquets
internal:parent_idIndex of parent row in previous level ParquetAll except sample
internal:relative_pathRelative path from DATA/ to this nodeAll Parquets
internal:offsetByte offset of this file inside the ZIP archiveZIP and TACOCAT
internal:sizeByte size of this file inside the ZIP archiveZIP and TACOCAT
internal:source_fileSource ZIP filenameTACOCAT only

Every Parquet MUST contain internal:current_id and internal:relative_path. Every Parquet except sample.parquet MUST also contain internal:parent_id. ZIP metadata MUST include internal:offset and internal:size for every data file.

Readers use these columns to build VSI paths. ZIP paths use the form /vsisubfile/{offset}_{size},{zip_path}. FOLDER paths use DATA/{idx}/{structure_path} and require no Parquet lookup.

7.3. ZIP Container

A ZIP container packages one dataset or partition in a .zip archive. Its CoZIP index MUST declare profile 2, the TACO profile. The byte-0 index MUST contain offsets to COLLECTION.json and every Parquet file in METADATA/. Every entry MUST use STORE mode so that /vsisubfile/ can access it directly.

The writer MUST use the .zip extension. Readers MUST identify TACO archives by their CoZIP profile byte, not by the filename, as defined in Section 14.5 of the CoZIP specification.

ZIP containers are immutable. Any update requires rebuilding the archive.

7.4. FOLDER Container

A FOLDER container is a plain directory with the same contents as a ZIP container. Converting between the two changes only the packaging.

New samples can be appended without rebuilding existing data, making FOLDER suitable for incremental datasets.

7.5. TACOCAT

TACOCAT makes a partitioned dataset queryable as one collection. It merges metadata from several ZIP files into a single directory.

.tacocat/
├── sample.parquet
├── children.parquet
├── children__before.parquet
├── children__after.parquet
└── COLLECTION.json

Each Parquet file combines the corresponding tables from the source ZIPs. The internal:source_file column MUST identify the source of every row. DuckDB can then query all metadata without opening the ZIP files.

When data is requested, the reader combines internal:source_file, internal:offset, and internal:size into a VSI path to the correct ZIP.

TACOCAT consolidation MUST verify that every partition uses the same contract. Its COLLECTION.json combines the partition metadata, sample counts, spatial extents, and temporal extents.

taco:sources SHOULD retain the extent of each partition. Readers can use this information to find relevant ZIP files without opening every partition.

{
  "taco:sources": {
    "count": 3,
    "files": ["europe.zip", "asia.zip", "americas.zip"],
    "extents": [
      {"file": "europe.zip", "spatial": [-10, 30, 45, 70], "temporal": ["2023-01-01", "2023-12-31"]},
      {"file": "asia.zip", "spatial": [60, -10, 150, 55], "temporal": ["2023-01-01", "2023-12-31"]},
      {"file": "americas.zip", "spatial": [-170, -55, -35, 75], "temporal": ["2023-01-01", "2023-12-31"]}
    ]
  }
}

8. API Layer

TACO has one writing API and may have many reading APIs. Datasets MUST be written through the public API of the taco package. Alternative writer implementations are not permitted. Readers MAY use any interface as long as they interpret the format correctly.

8.1. taco (Writer)

taco is the only TACO writer. The public entry point is taco.open_writer() for both ZIP and FOLDER containers. A path ending in .zip selects ZIP. A path without a suffix selects FOLDER. Other suffixes are rejected.

Data objects

TACO uses small immutable data objects for structure. Contract defines the structure and metadata schema. Collection describes the dataset. Sample contains one sample, and Asset points to one source file.

MetadataSchema contains one or more Level objects. Each level associates a namespace with a Pydantic model or a derived metadata group.

Metadata schema

taco.metadata provides reusable groups such as STAC and Raster. Datasets may use these models, extend them, or define additional Pydantic models.

import taco
from pydantic import BaseModel, Field


class ML(BaseModel):
    split: str = Field(description="Dataset split")


contract = taco.Contract(
    structure=["image.tif", "label.tif"],
    metadata=taco.MetadataSchema(
        taco.Level(
            "sample",
            stac=taco.metadata.STAC,
            ml=ML,
            majortom=taco.metadata.MajorTOM(dist_km=100),
        ),
        taco.Level("children", raster=taco.metadata.Raster),
    ),
)

The keyword is the namespace. The Pydantic model defines its fields, types, nullability, and descriptions. The writer stores them as qualified columns such as stac:geometry, ml:split, and raster:resolution.

A union with None makes a field nullable. Field(description=...) supplies its description. Exact Arrow types may use Annotated.

from datetime import datetime
from typing import Annotated

import pyarrow as pa

Float32 = Annotated[float, pa.float32()]
TimestampUTC = Annotated[datetime, pa.timestamp("us", tz="UTC")]

The serialized contract contains the resulting columns, not Python class names, import paths, defaults, or validators.

Sample metadata

Metadata is attached to the object it describes. Sample.metadata describes the sample, while Asset.metadata describes a file. The writer assigns each object to the correct metadata level.

Assets are passed as a list. In a flat structure, the contract path is inferred when the source filename matches it, so the name is not repeated. The path argument is required for nested paths or when the source name differs from the contract.

sample = taco.Sample(
    metadata=taco.Metadata(
        stac=taco.metadata.STAC(...),
        ml=ML(split="train"),
    ),
    assets=[
        taco.Asset(
            Path("/data/image.tif"),
            metadata=taco.Metadata(
                raster=taco.metadata.Raster(resolution=10, num_bands=13)
            ),
        ),
        taco.Asset(
            Path("/data/label.tif"),
            metadata=taco.Metadata(
                raster=taco.metadata.Raster(resolution=10, num_bands=1)
            ),
        ),
    ],
)

Derived metadata

A derived group declares the columns it needs and the columns it produces. MajorTOM requires stac:centroid and produces majortom:code. The contract is invalid when a required column is missing.

Samples do not provide values for derived groups. The writer computes them from batches of validated metadata before writing Parquet. This keeps vectorized operations in Arrow, NumPy, or Shapely instead of running them once per sample.

The configuration of a derived group is part of the contract. Appending data with different settings is not allowed.

Writer lifecycle

add() and extend() validate and stage samples. They do not modify the final dataset.

run() closes the input, computes derived metadata and ZIP offsets, writes each Parquet file once, and publishes the result. If a build fails, an existing dataset MUST remain unchanged.

Leaving the context manager only removes temporary files. It does not call run(). Calling run() again after success returns the same result without rebuilding.

FOLDER containers may use append=True. ZIP containers may be partitioned. Each ZIP partition is published independently, so a complete partitioned release and its TACOCAT directory are not one filesystem transaction.

Example

from datetime import datetime, timezone
from pathlib import Path

import taco
from pydantic import BaseModel, Field
from shapely.geometry import Point


class ML(BaseModel):
    split: str = Field(description="Dataset split")


contract = taco.Contract(
    structure=["image.tif", "label.tif"],
    metadata=taco.MetadataSchema(
        taco.Level(
            "sample",
            stac=taco.metadata.STAC,
            ml=ML,
            majortom=taco.metadata.MajorTOM(dist_km=100),
        ),
        taco.Level("children", raster=taco.metadata.Raster),
    ),
)

collection = taco.Collection(
    contract=contract,
    id="cloud-segmentation",
    dataset_version="1.0.0",
    description="Cloud segmentation dataset",
    licenses=["CC-BY-4.0"],
    providers=[{"name": "CSIC", "roles": ["producer"]}],
    tasks=["segmentation"],
)

point = Point(-76.5, -9.2)
sample = taco.Sample(
    metadata=taco.Metadata(
        stac=taco.metadata.STAC(
            geometry=point.wkb,
            centroid=point.wkb,
            crs="EPSG:4326",
            time_start=datetime(2025, 1, 1, tzinfo=timezone.utc),
        ),
        ml=ML(split="train"),
    ),
    assets=[
        taco.Asset(
            Path("/data/image.tif"),
            metadata=taco.Metadata(
                raster=taco.metadata.Raster(resolution=10, num_bands=13)
            ),
        ),
        taco.Asset(
            Path("/data/label.tif"),
            metadata=taco.Metadata(
                raster=taco.metadata.Raster(resolution=10, num_bands=1)
            ),
        ),
    ],
)

with taco.open_writer(collection, "clouds.zip") as writer:
    writer.add(sample)
    writer.run()

8.2. DuckDB Extension (Reader)

The reference reader is part of the CoZIP DuckDB extension. Every DuckDB client uses the same SQL interface. Remote access goes through DuckDB's filesystem layer, including httpfs.

INSTALL cozip FROM community;
LOAD cozip;

read_taco(path, idx, level, pivoted, files, gdal_vsi)

read_taco returns a table and detects ZIP, FOLDER, or TACOCAT from the path.

path is required and accepts any local or remote filesystem supported by DuckDB, including HTTP, S3, Azure, GCS, and Hugging Face. For ZIP containers, DuckDB reads the byte-0 index and scans the indexed Parquet ranges with predicate and projection pushdown.

SELECT * FROM read_taco('/data/cloudsen12.zip');
SELECT * FROM read_taco('s3://bucket/cloudsen12.zip');
SELECT * FROM read_taco('https://example.com/cloudsen12.zip');
SELECT * FROM read_taco('hf://datasets/tacofoundation/cloudsen12/cloudsen12.zip');

idx selects samples by their integer position. NULL returns all samples, an integer returns one sample, and a two-element list returns a range.

SELECT * FROM read_taco('dataset.zip');                -- all samples
SELECT * FROM read_taco('dataset.zip', idx=5);         -- sample 5
SELECT * FROM read_taco('dataset.zip', idx=[0, 100]);  -- first 100 samples

level selects a metadata level. NULL returns the default joined view. A level name reads its Parquet directly without joins.

SELECT * FROM read_taco('dataset.zip');                         -- joined view
SELECT * FROM read_taco('dataset.zip', level='sample');          -- sample.parquet
SELECT * FROM read_taco('dataset.zip', level='children');        -- children.parquet
SELECT * FROM read_taco('dataset.zip', level='children/before'); -- children__before.parquet

pivoted controls the result shape. The default value is true, which returns one row per sample and one VSI path column per selected file. When false, the result contains one row per file with path and cozip:gdal_vsi columns.

files limits which structure paths appear in a pivoted result. NULL returns all of them. This option is ignored when level is set.

gdal_vsi controls whether path columns contain GDAL VSI paths. The default is true. When false, path columns are NULL, which allows metadata-only queries.

-- Pivoted (default), one row per sample, one column per file
SELECT * FROM read_taco('cloudsen12.zip');
-- sample_id | ml:split | quality:cloud_cover | s2_l1c          | s2_l2a          | target
-- 0         | train    | 23.5                | /vsisubfile/... | /vsisubfile/... | /vsisubfile/...

-- Flat, one row per file
SELECT * FROM read_taco('cloudsen12.zip', pivoted := false);
-- sample_id | ml:split | raster:resolution | raster:num_bands | path       | cozip:gdal_vsi
-- 0         | train    | 10.0              | 13               | s2_l1c.tif | /vsisubfile/...
-- 0         | train    | 10.0              | 13               | s2_l2a.tif | /vsisubfile/...
-- 0         | train    | 10.0              | 1                | target.tif | /vsisubfile/...

-- Two selected files
SELECT * FROM read_taco('change_detection.zip', files := ['before/B02.tif', 'after/B02.tif']);
-- sample_id | ml:split | before/B02.tif  | after/B02.tif

A variable sequence such as img*[4,16].tif becomes a LIST(VARCHAR) column in the pivoted view.

SELECT * FROM read_taco('multitemporal_s2.zip');
-- sample_id | ml:split | series:num_images | vsi_path
-- 0         | train    | 4                 | [/vsisubfile/..., /vsisubfile/..., ...]
-- 1         | val      | 8                 | [/vsisubfile/..., /vsisubfile/..., ...]

taco_contract(path)

taco_contract returns the contract as kind and value rows. The extension also provides taco_structure, taco_levels, and taco_collection for direct inspection. taco_sql shows the SQL generated by read_taco.

8.3. Language clients

Any DuckDB client can call the reader directly. The Python package also provides a small wrapper.

Python

import taco

table = taco.reader.read("cloudsen12.zip")
table = taco.reader.read("cloudsen12.zip", idx=5)
table = taco.reader.read("cloudsen12.zip", idx=[0, 100], pivoted=False)
table = taco.reader.read("cloudsen12.zip", level="sample")

description = taco.reader.contract("cloudsen12.zip")

The wrapper manages a DuckDB connection and returns Arrow tables. All reading logic remains in the extension.

9.2. Contract vs PIT

The main change in v3 is that the dataset structure is explicit.

In v2, the writer inferred the structure from the first sample. PIT then required later samples to have the same children, in the same positions, with the same types. Missing positions were filled with __TACOPAD__ placeholders.

In v3, the contract declares the file layout and metadata schema before writing begins. Every sample is checked against it. Nothing is inferred and no padding is needed.

The contract also determines the Parquet files in advance. Their names describe the rows they contain, such as children__before.parquet, instead of using a depth such as level1.parquet. Variable sequences replace padding when the number of files differs between samples.

9.3. Metadata System

v2 stored metadata twice. Consolidated levelX.parquet files supported queries across the dataset, while local __meta__ files supported navigation inside each folder.

v3 stores all metadata in the Parquet files under METADATA/. Relationships between levels use internal:parent_id and SQL joins. Local __meta__ files are no longer needed because the contract already describes every level.

9.4. Reader Architecture

v2 used a Python reader with separate backends for ZIP, FOLDER, and TACOCAT. DuckDB was hidden behind TACO-specific dataset and dataframe classes.

v3 moves reading into the CoZIP DuckDB extension. It exposes read_taco() and inspection functions through SQL, detects the container, and builds paths internally. Every DuckDB client uses the same implementation, with an optional convenience wrapper for Python.

9.5. Extension System

v2 extensions combined schema definitions with metadata computation through base classes and extend_with().

v3 uses namespaced Pydantic models in the contract. The namespace determines the stored column prefix, and the model defines and validates its fields.

taco includes reusable models such as STAC and Raster. It also provides derived groups such as MajorTOM, which compute metadata by batch from explicit dependencies. Datasets can use the built-in groups, extend their models, or define additional groups.

9.6. TACOCAT and TACOLLECTION

v2 stored TACOCAT in a binary file with a fixed header. It used a separate TACOLLECTION JSON document for dataset metadata.

v3 stores TACOCAT as a .tacocat/ directory containing merged Parquet files and one COLLECTION.json. The taco:sources field replaces TACOLLECTION.

9.7. Migration Path

There is no automatic migration tool. The two versions differ in structure discovery, sample identity, metadata layout, and Parquet naming.

To migrate, producers MUST define a v3 contract and rebuild the dataset with taco. The GeoTIFF, NetCDF, and other data files can remain unchanged. Only their packaging and metadata must be rewritten.

Annex B: History

TACO began in Valencia, Spain, at the Image and Signal Processing group of the Universitat de València. Early discussions brought together Julio Contreras, Oscar Pellicer, Simon Donike, Chen Ma from HIT, and David Montero from the University of Leipzig.

During that period, after spending more than a month harmonizing cloud detection datasets, we sketched a general solution. We wanted something simple for our own work and the datasets produced at ISP. That idea became TACOv1, which combined a custom binary layout with Parquet metadata and built its tooling around GDAL and dataframes.

The first format had many flaws, but its central idea held up. Conversations at ESA Living Planet 2025 shaped TACOv2. Jérémy Anger from Kayrros and Université Paris-Saclay suggested replacing the custom binary format with ZIP. Discussions with Mikolaj Czerkawski at Asterisk about MajorTOM influenced the lazy loading design. Nils Lehmann and Adam Stewart from the University of Munich and TorchGeo brought years of experience with machine learning datasets to the API design.

OceanTACO, built with Nils Lehmann at TUM, tested v2 on ocean remote sensing data and exposed limitations that later shaped the v3 contract. Nate Mankovich at ISP helped define the Position-Invariant Tree that underpinned v2. Luis Gómez-Chova and Gustau Camps-Valls at ISP have helped question and refine TACO from the beginning.

TACOv2 worked. We published datasets, people used them, and the tools held up for small and medium collections. Asterisk Labs then used TACO to build datasets at production scale. Each dataset revealed another limit of v2.

TACOv3 is smaller than v2. The contract replaces PIT, extensions, and padding. One DuckDB extension replaces three Python reader backends. Local __meta__ files and the binary TACOCAT header are gone.

The original idea remains the same. Data and metadata should live together so that a machine learning researcher can query, filter, and load a dataset without thinking about its packaging.
